## 1. 产品概述

### 1.1 Kayak 是什么
Kayak 是一个面向科学研究团队的实验数据采集与管理平台。它帮助科研人员：

- 连接和管理多种科学仪器（通过虚拟模拟器、Modbus 等工业协议）
- 定义和执行标准化试验流程
- 实时采集、存储和可视化传感器数据
- 在团队中协作共享工作台和试验资源

### 1.2 本次重构目标
用户反馈当前前端存在架构性问题，需要**彻底重构**。重构的核心诉求：
- **界面完全由数据驱动**：一切 UI 状态来自后端数据，操作只将指令发送给后端
- **用户体验流畅**：无歧义的状态反馈，完善的三态处理（加载中 / 有数据 / 错误或空）
- **功能完整可用**：每一个用户故事都能走通完整的业务流程

### M1 认证与身份管理

#### 用户故事

| ID | 作为... | 我想要... | 以便... | 优先级 |
|----|---------|----------|--------|:------:|
| US-AUTH-001 | 新用户 | 注册一个 Kayak 账号 | 能够使用平台功能 | **Must** |
| US-AUTH-002 | 已注册用户 | 使用邮箱和密码登录 | 访问我的工作数据和资源 | **Must** |
| US-AUTH-003 | 已登录用户 | 在关闭浏览器后重新打开时自动保持登录状态 | 不需要每次都输入密码 | **Must** |
| US-AUTH-004 | 已登录用户 | 从任何位置安全退出 | 保护我的账号不被他人使用 | **Must** |
| US-AUTH-005 | 会话过期用户 | 看到友好的提示并重新登录 | 不会因为被强制退出而感到困惑 | **Should** |
| US-AUTH-006 | 已登录用户 | 看到当前登录的用户信息和头像 | 确认我在使用正确的账号 | **Should** |
| US-AUTH-007 | 用户 | 修改我的密码和个人信息 | 维护账号安全 | **Nice** |

#### 验收标准

1. **登录页面**：
   - 显示用户名/邮箱输入框和密码输入框
   - 输入不完整时，"登录"按钮不可点击
   - 登录失败时，显示具体错误原因（账号不存在、密码错误、网络错误等），**错误信息使用用户可理解的语言**
   - 登录成功后，自动跳转到用户上次访问的页面（或首页）
   - 若重定向来自被保护的页面，登录成功后返回原页面

2. **注册页面**：
   - 输入邮箱、密码、用户名（可选）
   - 密码强度提示
   - 注册成功后提示用户去登录

3. **会话管理**：
   - 访问令牌过期后自动使用刷新令牌续期
   - 若刷新也失败，用户被重定向到登录页面并显示"会话已过期，请重新登录"
   - 应用启动时检查是否有有效会话，有则直接进入，无则显示登录页

4. **启动流程**：
   - 应用启动 → 显示加载动画 → 检查本地会话 →
     - 有效 → 直接进入首页
     - 无效 → 跳转登录页
   - 加载时间超过 3 秒时，显示"正在加载..."提示

#### 关键状态

| 状态 | 界面表现 |
|------|----------|
| 加载中（检查会话） | 全屏居中加载动画 + "正在初始化..." |
| 未登录 | 登录页 |
| 登录中 | 按钮显示加载状态，禁用输入 |
| 登录失败 | 错误横幅，可关闭 |
| 已登录 | 正常进入应用 |

7. **错误处理**：
   - 无权限操作 → 显示"您没有权限执行此操作"
   - 团队不存在 → 显示"团队不存在或已被删除"

### M5 设备管理

#### 用户故事

| ID | 作为... | 我想要... | 以便... | 优先级 |
|----|---------|----------|--------|:------:|
| US-DEV-001 | 用户 | 在一个工作台中添加设备 | 将仪器接入系统 | **Must** |
| US-DEV-002 | 用户 | 以树形结构查看设备层级关系 | 理解设备之间的连接关系 | **Must** |
| US-DEV-003 | 用户 | 编辑设备信息（名称、协议类型） | 更新设备配置 | **Must** |
| US-DEV-004 | 用户 | 删除设备 | 移除不再使用的仪器 | **Must** |
| US-DEV-005 | 用户 | 配置设备的通信协议参数 | 正确连接到物理/虚拟仪器 | **Must** |
| US-DEV-006 | 用户 | 测试设备连接是否正常 | 在实验前确认设备可用 | **Should** |
| US-DEV-007 | 用户 | 查看设备的在线/离线状态 | 快速了解设备可用性 | **Should** |
| US-DEV-008 | 用户 | 创建设备的子设备 | 表示级联/嵌套的仪器拓扑 | **Nice** |

#### 验收标准

1. **设备树**：
   - 树形展示所有设备及其父子关系
   - 每个节点显示设备名、状态指示灯 + 协议图标
   - 点击展开/折叠子设备
   - 点击节点选中设备，右侧显示详情
   - 支持添加/编辑/删除设备操作

2. **添加设备**：
   - 选择父设备（可选，无则创建在根节点）
   - 输入名称（必填）
   - 选择协议类型：Virtual / Modbus TCP / Modbus RTU / CAN / VISA / MQTT
   - 根据协议类型显示对应的配置表单：
     - **Virtual**: 虚拟模式（Random/Fixed/Sine/Ramp）、数据类型、取值范围
     - **Modbus TCP**: 主机地址、端口、从站ID、超时
     - **Modbus RTU**: 串口号、波特率、数据位、停止位、校验位、从站ID

3. **设备状态**：
   - 在线 🟢 / 离线 ⚫ / 错误 🔴
   - 状态自动刷新（WebSocket 推送或轮询）

4. **连接测试**（Modbus 设备）：
   - 点击"测试连接"按钮
   - 显示测试结果：成功（含延迟）/ 失败（含原因）

#### 验收标准

1. **测点列表**：显示每个测点的名称、类型、访问权限（RO/WO/RW）、状态、当前值（含单位）

   - 名称（必填）

   - 访问权限：Read Only / Write Only / Read Write
3. **Modbus 测点**：额外需要 寄存器类型、起始地址、数据格式
4. **实时数值**：通过 WebSocket 订阅测点数值，自动更新显示；状态指示：正常 / 超时 / 异常

## 6. 数据驱动原则说明

### 6.1 核心理念
> **界面是数据的投影，操作是向数据发送指令。**

每一个页面和组件都应遵循以下原则：

1. **单一数据源**：前端的所有业务状态都来自后端 API。前端不做业务数据的"本地缓存"——已有的缓存机制（Token 等认证信息除外）应消除或最小化。
2. **操作即指令**：用户在界面上的每一个操作（创建、编辑、删除、执行）都应转化为对后端 API 的调用。前端不自行计算或推导业务结果。
3. **状态驱动 UI**：每个组件都有明确的三态（Loading / Data / Error+Empty），UI 根据数据状态自动切换呈现，而非通过本地标志位控制。

### 6.2 对重构的具体指导

| 当前问题 | 重构方向 |
|----------|----------|
| 组件内部维护本地数据和状态副本 | 组件只消费 Provider 提供的后端数据，不做本地复制 |
| 操作结果没有统一反馈机制 | 所有 API 操作结果统一通过状态管理分发，UI 自动响应 |
| 界面中有硬编码的占位符（如仪表盘统计 "-"） | 所有数据必须来自后端；无数据时显示适当空状态 |
| 复杂页面的多个子组件分别请求相同数据 | 统一数据获取层，避免重复请求和状态不一致 |

### 6.3 数据流模型

```
┌─────────┐    HTTP/WS    ┌──────────┐    Provider    ┌──────────┐
│ Backend │ ────────────→ │ Service  │ ────────────→ │  State   │
│  API    │ ←──────────── │  Layer   │ ←──────────── │ Notifier │
└─────────┘               └──────────┘               └────┬─────┘
                                                          │
                                                    ┌─────▼─────┐
                                                    │   UI      │
                                                    │ Widgets   │
                                                    └───────────┘
```

- UI 通过 `ref.watch(provider)` 消费数据
- UI 通过 `ref.read(provider.notifier).doSomething()` 发送用户操作
- Notifier 调用 Service 层，Service 层调用后端 API
- Notifier 更新 State，UI 自动重新渲染

## 7. 交互设计原则

1. **每个操作都应有反馈**：点击按钮后，按钮应显示加载状态；操作结果（成功/失败）应通过 Toast 或内联消息明确告知用户
2. **三态全覆盖**：每个数据驱动的界面区域必须有 Loading / Loaded(有数据) / Error+Empty 三个状态的可视呈现
3. **错误信息人性化**：后端返回的技术错误码（如 500、ConnectionRefused）应转换为用户可理解的中文提示
4. **不可逆操作需确认**：删除、停止等操作必须弹出确认对话框
5. **响应式布局**：从手机（< 600px）到桌面（> 1200px）均有合理布局
6. **无障碍访问**：所有图标按钮应有 tooltip，表单元素应有 label/aria-label
7. **键盘导航**：主要操作应是键盘可访问的（桌面场景）

## 8. 待向用户澄清的问题

以下问题需要用户（或相关利益方）在开始开发前明确回答。这些问题直接影响需求范围和优先级排序。

### Q1: 用户角色与权限模型
> 当前代码定义了 Team Owner / Admin / Member 三级角色 + 独立用户，Viewer 角色只在概念层面存在。
1. **Viewer（观察者）角色是否需要在 Release 3 中实现？**
2. **Team Admin 和 Team Member 在工作台/设备/方法上的操作权限细节是什么？**（见 §2 权限矩阵中标记 ❓ 的项）
3. **独立用户（不属于任何团队）的资源是否可以被团队查看？是否需要"分享"功能？**

### Q2: 注册与邀请策略
1. **用户注册是否需要管理员审核？还是开放自助注册？**
2. **邀请链接的有效期和通知方式？**（当前代码是 7 天过期）
3. **是否需要"通过邮箱验证码验证"的注册流程？**

### Q3: 工作台 vs 试验的关系
> 当前代码中，工作台管理设备和测点，试验引用方法，但**工作台和试验之间没有明确的关联**。
1. **一个试验是否需要绑定到一个工作台？** 即：执行试验时，使用哪个工作台的设备？
2. 如果不需要绑定，**试验执行时如何知道要操作哪些设备？**

### Q4: 设备协议支持范围
> 设备模型中定义了多种协议类型（CAN、VISA、MQTT），但当前后端只实现了 Virtual、Modbus TCP、Modbus RTU。
1. **Release 3 前端是否只需要支持这三种已实现的协议？还是需要为 CAN / VISA / MQTT 预留界面？**
2. **每种协议的配置表单字段是否已经稳定，还是会频繁变更？**

### Q5: 实时数据与 WebSocket
> 当前试验执行控制台使用 WebSocket 接收日志和状态推送。
1. **测点实时数值是否也通过 WebSocket 推送？更新频率是多少？**
2. **设备在线状态是否需要通过 WebSocket 实时更新？**
3. **前端是否需要在连接断开时自动重连？重连间隔和次数策略是什么？**

### Q6: 数据导出
> 代码中出现了"数据文件管理"的快捷入口但路由到了设置页，说明尚未实现。
1. **用户是否需要从前端下载 HDF5 数据文件？**
2. **是否需要导出 CSV / Excel 格式的数据？**
3. **数据分析图表是否需要"导出为图片"功能？**

### Q7: 国际化优先级

1. **Release 3 是否必须完成完整的中英文国际化？**

### Q8: 移动端支持
