## 1. 版本概述

### 1.1 版本目标

Release 3 是 **修复与体验提升版本**，核心目标只有一个：

> **让 Kayak 平台能够被用户真正使用起来。**

Release 1 和 Release 2 已经完成了大量功能的后端与前端服务层开发，但几个关键 Bug 和体验问题导致这些功能对用户不可见、不可用。Release 3 专注于清除这些阻塞性缺陷，使平台从"有功能但不能用"变为"可用且好用"。

### 1.2 用户当前的痛点

作为产品负责人，我从用户的视角总结了以下真实体验：

| 序号 | 用户做了什么 | 发生了什么 | 用户的感受 |
|------|------------|-----------|-----------|
| 1 | 打开浏览器，输入账号密码，点击"登录" | 页面转圈 1 秒，按钮变绿，但**停留在登录页**，始终无法进入系统 | "我明明登录成功了，为什么进不去？这软件是不是坏了？" |
| 2 | 反复尝试登录均失败 | 无任何有用的错误提示 | "它到底哪里出了问题？" |
| 3 | 想退出当前账号换一个账号 | 找不到退出按钮 | "我该怎么退出？关掉浏览器吗？" |
| 4 | 关闭标签页后重新打开 | 又回到了登录页，之前的状态全没了 | "我刚才不是登录过吗？怎么又要重新来？" |
| 5 | 页面整体是深色调 | 某些文字不够清晰，对比度不足 | "看着有点费眼睛。" |
| 6 | 切换到中文界面 | 很多地方还是英文，或者翻译很生硬 | "说好的中文支持呢？这算哪门子的多语言？" |
| 7 | 想查阅用户手册了解如何使用 | 手册里没有截图，描述和实际界面也对不上 | "这手册到底在说哪个版本？" |

### 1.3 本版本不做什么

**Release 3 严格限定于修复已有缺陷，不新增任何功能。** 以下内容明确排除：

| 排除项 | 原因 | 计划 |
|--------|------|------|
| 新协议驱动（CAN/VISA/MQTT） | 属于功能扩展，非缺陷修复 | Release 5+ |
| 完整的 UI 重新设计 | 当前 Material Design 3 框架可用，仅需修复对比度问题 | Release 5+（需 sw-anna 参与） |
| 新功能页面或路由 | 不属于修复范围 | Release 5+ |
| 移动端适配 | 当前仅桌面 Web 部署 | Release 5+ |
| 性能优化 | 核心功能尚未验证之前不宜过早优化 | Release 5+ |
| 邮件邀请集成 | 团队功能 Phase 2，非缺陷 | Release 5+ |

## 3. 功能需求

### 3.1 FR-AUTH-001：修复登录流程

**优先级**: 🔴 P0 (Blocker)  
**关联用户故事**: US-001  
**预估工作量**: 2-4 小时

#### 需求描述

当前登录表单（`login_form.dart`）在第 91 行使用了模拟登录逻辑（`Future.delayed` + `loginProvider.setSuccess()`），从未调用真正的认证链路 `AuthStateNotifier.login()` → `AuthApiService.login()` → 后端 `POST /api/v1/auth/login`。

这导致：
1. 后端从未收到认证请求
2. 全局 `AuthState` 的 `isAuthenticated` 始终为 `false`
3. `GoRouter` 的路由守卫永远不会触发从 `/login` 到 `/dashboard` 的跳转
4. 用户看到的"登录成功"只是局部状态欺骗，实际上从未登录

#### 修复方案

将 `LoginForm._submitForm()` 中的模拟登录替换为调用真正的认证链路：

```dart
// 当前（错误）: login_form.dart L91
Future.delayed(const Duration(seconds: 1), () {
  if (mounted) {
    ref.read(loginProvider.notifier).setSuccess();
  }
});

// 修复后（正确）:
await ref.read(authStateProvider.notifier).login(email, password);
```

同时需要处理：
- **加载状态**: 在调用 `authStateNotifier.login()` 期间，`loginProvider` 应显示 `loading` 状态
- **错误处理**: 如果 `authStateNotifier.login()` 抛出异常（如 401 认证失败、网络错误），应捕获异常并通过 `loginProvider` 显示可读的错误信息
- **成功跳转**: 登录成功后，`AuthState.authenticated()` 会自动设置 `isAuthenticated = true`，`GoRouter.redirect` 将自动触发跳转到 `/dashboard`——无需在 `LoginForm` 中手动处理导航

#### 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| AC1 | 用户输入 `admin@kayak.local` / `Admin123` 点击登录后，后端 `POST /api/v1/auth/login` 被实际调用（可通过后端日志确认） | 手动验证 + 后端日志检查 |
| AC2 | 登录成功后，浏览器自动跳转到 Dashboard 页面（`/dashboard`），不再停留在登录页 | 手动验证 |
| AC3 | 输入错误的密码时，登录页显示可读的错误提示信息（如"登录失败，请检查您的凭据"），不显示技术性错误 | 手动验证 |
| AC4 | 登录过程中，登录按钮显示加载状态（如"登录中..."），不可重复点击 | 手动验证 |
| AC5 | 登录成功后，浏览器的开发者工具 Application 标签中可以看到存储的 Token（access_token） | 手动验证 |
| AC6 | 刷新页面后，如果 Token 有效，用户应直接进入 Dashboard 而非登录页 | 手动验证 |

### 3.2 FR-AUTH-002：添加退出登录 UI 入口

**优先级**: 🔴 P0 (Blocker)  
**关联用户故事**: US-002  
**预估工作量**: 2-3 小时

#### 需求描述

`AuthStateNotifier.logout()` 已经完整实现（清除 Token + 重置状态为 `AuthState.initial()`），`GoRouter` 的路由守卫也正确地会在 `isAuthenticated = false` 时重定向到 `/login`。但是，**前端没有任何 UI 入口允许用户触发退出登录操作**。

用户目前被迫通过关闭浏览器标签页来"退出"——这在 Web 环境下甚至无法真正清除 Token（Token 在 `localStorage` 中）。

#### 修复方案

在以下位置添加"退出登录"入口：

1. **设置页面（`/settings`）**：添加"退出登录"操作项（最高优先级）
2. **AppBar 用户头像区域**：在用户头像或用户名旁边添加下拉菜单，包含"退出登录"选项（如果实现简单）
3. **侧边导航栏底部**：添加"退出登录"导航项（备选方案）

**优先实现方案**：在设置页面中添加"退出登录"操作项。这是改动最小、最可控的方案。

**退出行为**：
- 点击"退出登录"时，弹出确认对话框："确定要退出登录吗？"
- 用户确认后，调用 `authStateNotifier.logout()`
- 清除所有持久化 Token
- 自动跳转到登录页，并显示提示："您已安全退出"

#### 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| AC1 | 在设置页面中存在"退出登录"操作入口 | 手动验证 |
| AC2 | 点击"退出登录"后弹出确认对话框 | 手动验证 |
| AC3 | 确认退出后，用户被重定向到登录页面 | 手动验证 |
| AC4 | 退出后，浏览器的 Token 存储被清除（开发者工具 Application 中无 Token） | 手动验证 |
| AC5 | 退出后，即使手动访问 `/dashboard` 或其他受保护路由，也被重定向到登录页 | 手动验证 |
| AC6 | 退出后，登录页显示"您已安全退出"的友好提示 | 手动验证 |

### 3.3 FR-AUTH-003：Web 环境下 Token 持久化可靠性

**优先级**: 🟡 P1 (High)  
**关联用户故事**: US-003  
**预估工作量**: 2-3 小时

#### 需求描述

当前 `token_storage.dart` 的 `TokenStorageInterface.create()` 方法中，Web 平台使用 `SecureTokenStorage`（基于 `flutter_secure_storage`），而桌面平台使用 `SharedPrefsTokenStorage`（基于 `shared_preferences`）。

`flutter_secure_storage` 在 Web HTTP localhost 环境下可能存在兼容性问题：
- 它的 Web 后端依赖浏览器的 `localStorage` 或 IndexedDB
- 在某些情况下可能静默失败，导致 Token 无法写入
- 该库的 Web 支持文档明确标注为"实验性"

#### 修复方案

修改 `TokenStorageInterface.create()`，使 Web 平台也使用 `SharedPrefsTokenStorage`：

```dart
// token_storage.dart — 修复后
static TokenStorageInterface create({required bool isWeb}) {
  if (!kIsWeb) {
    // 桌面平台：使用 SharedPreferences（已有实现）
    return SharedPrefsTokenStorage();
  }
  // Web 平台：使用 SharedPreferences 代替 flutter_secure_storage
  return SharedPrefsTokenStorage();
}
```

**说明**：
- `shared_preferences` 在 Web 上使用浏览器的 `localStorage`，成熟且可靠
- 在 Kayak 的使用场景下（内网/本地部署），`localStorage` 的安全性已足够
- 如果用户需要 HTTPS 部署下的更高安全性，可考虑后续引入 IndexedDB 加密方案

#### 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| AC1 | 在 Web HTTP localhost 环境下，登录成功后 Token 被成功写入浏览器存储 | 手动验证（开发者工具 Application → Local Storage） |
| AC2 | 关闭浏览器标签页后重新打开，Token 仍然存在，用户保持登录状态 | 手动验证 |
| AC3 | 退出登录后，存储中的 Token 被正确清除 | 手动验证 |
| AC4 | 桌面平台（Linux/macOS/Windows）的 Token 存储功能不受影响 | 回归测试 |
| AC5 | 多次登录-退出循环后，Token 读写没有出现残留或错乱 | 手动验证 |

### 3.4 FR-DEVICE-001：虚拟设备创建入口

**优先级**: 🟡 P1 (High)  
**关联用户故事**: US-004  
**预估工作量**: 3-5 小时

#### 需求描述

后端 `VirtualDriver` 已完整实现，支持多种类型的虚拟设备（温度传感器、压力传感器、功率计等）。但当前前端没有任何引导或快捷入口帮助用户创建设备。对于没有真实硬件的新用户，他们无法验证平台的设备管理功能。

#### 修复方案

在设备管理页面（`/devices`）或工作台详情页面的设备列表区域，添加以下功能：

**方案一（推荐 — 改动最小）**：在工作台详情页的设备列表顶部添加"创建虚拟设备"按钮

```
┌────────────────────────────────────────────────┐
│  设备管理                        [创建虚拟设备]  │
├────────────────────────────────────────────────┤
│  (设备列表)                                     │
└────────────────────────────────────────────────┘
```

点击后弹出虚拟设备创建对话框：
- **设备名称**：文本输入（预填默认名称如"虚拟温度传感器-01"）
- **设备类型**：下拉选择，提供以下预设模板：
  - 🌡️ 温度传感器（4 通道，-50°C ~ 150°C，正弦波模拟）
  - 📊 压力传感器（2 通道，0 ~ 10 MPa，随机游走模拟）
  - ⚡ 功率计（3 通道：电压/电流/功率，阶跃模拟）
  - 📈 通用传感器（2 通道，用户自定义范围）
- **所属工作台**：默认为当前工作台
- 点击"创建"后，自动创建设备及其对应的测点

**方案二（备选）**：在 Dashboard 添加"快速开始"引导卡片，当用户还没有任何设备时提示创建虚拟设备。

#### 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| AC1 | 设备管理页面中存在"创建虚拟设备"的明确入口（按钮或引导卡片） | 手动验证 |
| AC2 | 用户可以通过对话框选择设备类型并一键创建虚拟设备 | 手动验证 |
| AC3 | 创建的虚拟设备及其测点自动出现在设备列表中 | 手动验证 |

### 3.6 FR-UI-001：修复深色主题对比度与一致性

**优先级**: 🟡 P1 (High)  
**关联用户故事**: US-006  
**预估工作量**: 4-6 小时

#### 需求描述

用户反馈"前端风格不美观，深色调徒有其表"。经过分析，当前深色主题存在以下具体问题：

1. **对比度不足**：某些文字在深色背景上对比度不够，阅读困难
2. **组件一致性**：部分卡片/按钮在不同页面使用了不一致的颜色方案
3. **硬编码颜色**：部分 UI 组件使用了硬编码颜色值（而非主题系统颜色），导致在深色/浅色切换时出现颜色不协调

#### 修复方案

**检查与修复范围**（按优先级排序）：

1. **文字颜色对比度**：
   - 确保所有正文文字与背景的对比度 ≥ 4.5:1（WCAG AA 标准）
   - 确保大号文字（≥ 18px 或 ≥ 14px 粗体）与背景的对比度 ≥ 3:1
   - 重点检查：侧边栏文字、表格内容、表单标签、统计数字

2. **组件颜色一致性**：
   - 消除所有硬编码颜色值（如 `Color(0xFF1E1E1E)`、`Colors.grey[800]`），统一使用主题系统
   - 确保 Card、Dialog、BottomSheet 等容器组件使用 `Theme.of(context).colorScheme.surface` 而非硬编码
   - 检查按钮、输入框、开关等交互组件在所有页面的颜色一致性

3. **页面级审查**：
   - Dashboard 统计卡片
   - 设备列表/详情页
   - 试验控制台（1016 行代码，可能有较多硬编码）
   - 设置页面
   - 团队管理页面

#### 验收标准

| # | 标准 | 验证方式 |
|---|------|----------|
| AC1 | 深色主题下，所有正文文字的对比度满足 WCAG AA 标准（≥ 4.5:1） | 使用浏览器 DevTools 对比度检查工具验证 |
| AC2 | 浅色主题和深色主题之间切换时，所有页面元素颜色正确切换，无残留颜色 | 手动验证（每个页面逐一检查） |

### 3.7 FR-L10N-001：修复中英文界面

**优先级**: 🟡 P1 (High)  
**关联用户故事**: US-007

#### 需求描述

用户反馈"中英文切换/显示存在问题"且"多语言支持徒有其表"。经过代码审查，发现以下具体问题：

3. **语言切换测试**：

4. **移除法语**（`fr`）：
   - 当前 `l10n.yaml` 仅声明了 `en` 和 `zh` 两种语言
   - 不存在 `app_fr.arb` 文件
