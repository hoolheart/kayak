## 1. 产品概述与目标

### 1.1 Kayak 是什么

Kayak 是一个面向科学研究团队的实验数据采集与管理平台。它帮助科研人员：

- 连接和管理多种科学仪器（虚拟模拟器、Modbus TCP/RTU 协议设备）
- 定义和执行标准化试验流程
- 实时采集、存储和可视化传感器数据
- 在团队中协作共享工作台和试验资源

### 1.2 Release 3 重写目标

本次是**全面前端重写**，而非重构。当前 `kayak-frontend/` 目录下的所有代码将被删除，从零开始重新开发。

重写的核心目标：

> **构建一个数据驱动、体验流畅、功能完整的全新前端应用，与现有后端 API 完全对齐。**

具体诉求：

1. **彻底的数据驱动**：界面是后端数据的投影。所有 UI 状态来自后端 API，用户操作即向后端发送指令。前端不复刻业务数据、不做本地推导。
2. **完整的三态覆盖**：每个数据驱动的界面区域，必须有 Loading（加载中）、Data（有数据）、Error/Empty（错误或空）三个状态的清晰可视呈现。
3. **功能完整可用**：每一个用户故事都能走通完整的端到端业务流程，不存在半成品路径。
4. **与技术债告别**：消除硬编码中文、假数据占位符、绕过状态管理的脏代码、散落的 WebSocket 管理逻辑等所有已知问题。

### 1.3 与后端的关系

- **后端代码不做任何修改**。前端严格调用现有 REST API（`/api/v1/*`）和 WebSocket（`/ws/experiments/{id}`）。
- **前端不引入后端尚未支持的字段或功能**。数据模型、字段限制、业务流程均以后端实际实现为准。
- 如果前端需求发现后端缺字段（如试验 → 工作台绑定），先与后端开发沟通确认后再做。

### 1.4 后端能力基线（前端依赖清单）

| 领域 | 后端已实现 API | 前端需对接 |
|------|---------------|-----------|
| 认证 | `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `GET /auth/me` | ✅ |
| 用户 | `GET /users/me`, `PUT /users/me`, `POST /users/me/password` | ✅ |
| 工作台 | `GET/POST /workbenches`, `GET/PUT/DELETE /workbenches/{id}` | ✅ |
| 设备 | `GET/POST /workbenches/{id}/devices`, `GET/PUT/DELETE /devices/{id}`, `POST connect/disconnect/test-connection`, `GET status` | ✅ |
| 测点 | `GET/POST /devices/{id}/points`, `GET/PUT/DELETE /points/{id}`, `GET/PUT value` | ✅ |
| 方法 | `GET/POST /methods`, `GET/PUT/DELETE /methods/{id}`, `POST /methods/validate` | ✅ |
| 试验控制 | `POST load/start/pause/resume/stop`, `GET status/history` | ✅ |
| 试验查询 | `GET /experiments`, `GET /experiments/{id}`, `GET history/data-file` | ✅ |
| 试验数据 | `POST /experiments/{id}/data/query` | ✅ |
| 协议 | `GET /protocols`, `GET /system/serial-ports` | ✅ |
| WebSocket | `WS /ws/experiments/{id}`（试验状态+日志推送） | ✅ |

## 2. 用户角色与权限

### 2.1 角色定义

与后端完全一致的简化角色模型：

| 角色 | 说明 | 典型场景 |
|------|------|----------|
| **个人用户（Individual）** | 不属于任何团队，管理个人资源 | 独立研究者使用 Kayak 管理自己的实验 |
| **Team Owner** | 团队创建者，拥有全部权限 | 创建团队、管理成员、删除团队 |
| **Team Admin** | 团队管理员，协助管理日常事务 | 管理成员、编辑团队信息 |
| **Team Member** | 团队普通成员 | 查看和使用团队资源、执行试验 |

> **已排除**：Viewer / Guest 角色不在本版本范围内。

### 2.3 注册策略

- **开放自助注册**：任何用户可通过邮箱+密码注册账号，无需管理员审核
- **无邀请码注册要求**：注册页面只需邮箱、密码、用户名（可选）
- 注册成功后自动登录并跳转首页

### 2.4 默认工作台

- 用户注册成功后，系统自动创建一个**默认个人工作台**（名称示例："我的工作台"）
- 默认工作台初始没有设备，用户可以后续添加
- 如果后端暂未实现自动创建，前端在用户首次登录且无工作台时引导创建

## 3. 架构约束与设计原则

### 3.1 数据驱动核心原则

> **界面是数据的投影，操作是向数据发送指令。**

每一个页面和组件都必须遵循：

1. **单一数据源**：所有业务状态来自后端 API 响应。前端不做业务数据的本地缓存或推导。只有认证 Token 和用户偏好（主题/语言）可在本地存储。
2. **操作即指令**：用户在界面上的每一个操作（创建、编辑、删除、执行）都转化为对后端 API 的调用。前端不自行计算业务结果。
3. **状态驱动 UI**：每个数据组件都有明确的三态（Loading / Data / Error+Empty），UI 根据状态自动切换，不使用本地布尔标志位控制。
4. **数据流单向**：`Backend API → Service Layer → State Notifier → UI Widget`，不可反向。

### 3.2 交互设计原则

| 原则 | 具体要求 |
|------|----------|
| **操作有反馈** | 点击按钮 → 按钮显示加载状态 → 操作完成 → Toast / 内联消息通知结果（成功/失败） |
| **三态全覆盖** | 每个列表、详情区、图表区必须有 Loading / Loaded / Error+Empty 的视觉状态 |
| **错误信息人性化** | 后端技术错误（如 500、ConnectionRefused）转换为用户可理解的语言；禁止直接展示技术细节 |
| **不可逆操作需确认** | 删除、停止执行等操作必须弹出二次确认对话框 |
| **无权限操作有提示** | 禁用按钮 + tooltip 说明原因，或点击后弹窗提示 |
| **未保存变更提醒** | 离开编辑态页面时如有未保存内容，弹窗确认"是否放弃更改" |

### 3.3 UI 规范

- **设计语言**：Material Design 3
- **主色调**：#1976D2（科技蓝）
- **双主题支持**：浅色 + 深色，默认跟随系统
- **字体**：等宽字体用于代码/日志区域；默认字体用于其他区域

#### 用户故事

| ID | 作为... | 我想要... | 以便... | 优先级 |
|----|---------|----------|--------|:------:|

| US-AUTH-002 | 已注册用户 | 使用邮箱和密码登录 | 访问我的工作数据 | P0 |

| US-AUTH-004 | 已登录用户 | 安全退出登录 | 保护我的账号安全 | P0 |
| US-AUTH-005 | 会话过期用户 | 看到友好的过期提示并重新登录 | 不被突然强制退出而困惑 | P0 |
| US-AUTH-006 | 已登录用户 | 查看和修改我的个人信息与密码 | 维护账号安全 | P1 |

#### 页面清单

| 页面 | 路径 | 功能 |
|------|------|------|
| 登录页 | `/login` | 邮箱+密码登录，注册跳转链接 |
| 注册页 | `/register` | 邮箱+密码+用户名（选填）注册 |
| 个人资料页 | `/profile` | 查看/修改个人信息、修改密码 |

#### 验收标准

**登录页面：**
1. 显示邮箱输入框和密码输入框，带有清晰的 label
2. 邮箱或密码为空时，"登录"按钮不可点击（视觉禁用）
3. 登录失败时，显示具体且友好的错误原因：
   - "该邮箱尚未注册"（账号不存在）
   - "密码错误，请重试"（密码错误）
   - "网络连接失败，请检查网络后重试"（网络错误）
4. 登录成功后，跳转到首页
5. 若用户从受保护页面被重定向而来，登录成功后返回原页面
6. "登录中"状态：按钮显示加载动画，输入框禁用

**注册页面：**
1. 邮箱输入框（必填）、密码输入框（必填）、用户名输入框（选填）
2. 密码强度提示（弱/中/强，基于长度和字符多样性）
3. 注册成功 → 显示成功提示 → 自动跳转登录页（或直接自动登录）
4. 注册失败 → 显示具体原因（邮箱已注册、密码太短等）

**会话管理：**
1. Access Token 过期前自动使用 Refresh Token 续期（提前 5 分钟刷新）
2. Refresh Token 也过期 → 清除本地 Token → 重定向登录页 → 提示"会话已过期，请重新登录"
3. 应用启动流程：
   - 显示全屏加载动画（Kayak Logo + "正在初始化..."）
   - 检查本地 Token → 有效则进入首页，无效则跳转登录页
   - 加载超过 3 秒时显示"正在连接服务器..."
   - 加载超过 10 秒时显示"服务器连接超时，请稍后重试" + "重试"按钮
4. 登出时清除所有本地存储的 Token 和缓存

**个人资料页：**
1. 显示当前用户信息：用户名、邮箱、注册时间
2. 可修改用户名（保存调用 `PUT /users/me`）
3. 修改密码：输入旧密码 + 新密码 + 确认新密码（调用 `POST /users/me/password`）

1. 卡片网格布局展示所有工作台，每张卡片包含：
   - 工作台名称
   - 描述摘要（最多 2 行，超出省略）
   - 状态标签（Active / Archived）
   - 创建时间（相对时间如"3 天前" + hover 显示精确时间）
2. 顶部搜索框：按名称关键词实时过滤
3. 空状态（首次使用，无工作台时）：
   - 居中插画 + "您还没有工作台"

4. 加载状态：骨架屏（卡片占位形状 + 浅色闪烁）

6. 每个工作台卡片点击进入详情页
7. 底部或顶部有"+ 新建工作台"按钮
8. 支持分页（后端分页，前端显示"共 N 个工作台"）

**创建工作台：**
1. 点击"新建" → 弹出创建对话框或全屏表单
2. 表单字段：
   - 名称（必填，最长 255 字符）
   - 描述（选填，多行文本）
   - 所有权类型（在团队场景下可选择个人/团队）
3. 创建成功 → 关闭对话框 → 刷新列表 → 新工作台卡片出现并高亮

**编辑工作台：**
1. 在工作台详情页或卡片菜单 → "编辑"
2. 弹出编辑对话框，预填现有值
3. 修改名称/描述 → 保存

**删除工作台：**
1. 在工作台详情页或卡片菜单 → "删除"
2. 弹出确认对话框："确定要删除工作台「XXX」吗？此操作不可撤销，工作台下的所有设备和测点也将被删除。"
3. 用户确认 → 执行删除 → 返回列表

**工作台详情页：**
1. 顶部信息区：工作台名称、描述、状态、创建时间
2. 主体区域：设备管理（见 M5 设备管理模块），左侧设备树 + 右侧详情面板
3. 操作按钮：编辑、删除（在详情页右上角）

#### 用户故事

| ID | 作为... | 我想要... | 以便... | 优先级 |

| US-DEV-001 | 用户 | 在选定工作台中添加设备 | 将仪器接入系统 | P0 |
| US-DEV-002 | 用户 | 以树形结构查看设备及其层级关系 | 理解设备连接关系 | P0 |
| US-DEV-003 | 用户 | 编辑设备信息 | 更新设备配置 | P0 |
| US-DEV-004 | 用户 | 删除设备 | 移除不再使用的仪器 | P0 |
| US-DEV-005 | 用户 | 根据协议类型配置设备通信参数 | 正确连接仪器 | P0 |
| US-DEV-006 | 用户 | 测试设备连接状态 | 实验前确认设备可用 | P1 |
| US-DEV-007 | 用户 | 查看设备在线/离线状态 | 快速了解设备可用性 | P1 |

#### 页面清单

设备管理集成在**工作台详情页**（`/workbenches/{id}`）中，不作为独立页面存在。

#### 验收标准

**设备树（左侧面板）：**
1. 树形结构展示工作台下所有设备及其父子关系
2. 每个节点显示：
   - 设备名称
   - 状态指示圆点：🟢 在线 / ⚫ 离线 / 🔴 错误
   - 协议类型小图标（Virtual / Modbus TCP / Modbus RTU）
3. 点击节点 → 选中该设备 → 右侧面板显示设备详情
4. 点击展开/折叠箭头 → 显示/隐藏子设备
5. 右键菜单或节点旁操作按钮：编辑、添加子设备、删除
6. 空状态（工作台无设备时）：树区域显示"该工作台下暂无设备"+"添加第一台设备"按钮
7. 顶部有"+ 添加设备"按钮

**添加设备（对话框/表单）：**
1. 选择父设备（可选，不选则创建在根节点）
2. 设备名称（必填）
3. 协议类型选择：**仅支持三种**
   - **Virtual（虚拟设备）**: 无需物理设备，用于开发测试
   - **Modbus TCP**: 通过 TCP/IP 网络连接 Modbus 设备
   - **Modbus RTU**: 通过串口连接 Modbus 设备
4. 根据协议类型动态显示配置表单：

   **Virtual 协议配置：**
   - 虚拟模式下拉选择：Random（随机值）/ Fixed（固定值）/ Sine（正弦波）/ Ramp（斜坡）
   - 数据类型：Number / Integer
   - 最小值、最大值
   - 更新间隔（毫秒）

   **Modbus TCP 协议配置：**
   - 主机地址（IP 或域名，必填）
   - 端口号（默认 502）
   - 从站 ID（1-247）
   - 超时时间（毫秒，默认 3000）

   **Modbus RTU 协议配置：**
   - 串口选择（调用 `GET /system/serial-ports` 获取可用串口列表）
   - 波特率（9600 / 19200 / 38400 / 57600 / 115200）
   - 数据位（7 / 8）
   - 停止位（1 / 2）

```
│  └─────────────────────────┘  └─────────────────────────┘ │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

**控制面板（左侧）：**
1. 试验信息摘要：工作台名、方法名、创建时间
2. 控制按钮组（根据当前状态动态启用/禁用）：
   - IDLE 状态：**载入**按钮可用，其他禁用
   - LOADED 状态：**开始**按钮可用，**载入**禁用
   - RUNNING 状态：**暂停**、**停止**可用，**载入**、**开始**、**继续**禁用
   - PAUSED 状态：**继续**、**停止**可用，其他禁用
   - COMPLETED / ERROR：所有控制按钮禁用
3. 按钮状态反馈：
   - 点击后按钮显示加载状态（防止重复点击）
   - 操作失败时 Toast 通知具体错误
4. 当前状态显眼展示（大文字 + 颜色标签）
5. 运行时长计时器（RUNNING/PAUSED 状态下实时更新）
6. 停止按钮点击后弹出确认对话框："确定要停止当前试验吗？"

**执行日志区（右侧）：**
1. 等宽字体显示日志流
2. 每条日志包含：
   - 日志级别标签（颜色区分）：INFO（蓝）/ WARN（橙）/ ERROR（红）/ DEBUG（灰）
   - 时间戳（HH:MM:SS）
   - 日志消息
3. 自动滚动到底部（当有新日志推送时）
4. 用户手动向上滚动时，右下角显示"↓ 新日志"浮动按钮，点击跳回底部
5. "清空日志"按钮（清除当前显示的日志历史）
6. 支持日志级别筛选（显示/隐藏 DEBUG 级别）

**WebSocket 管理：**
1. 进入控制台后自动连接 WebSocket（`/ws/experiments/{id}`）
2. WebSocket 连接状态指示：右上角 🟢已连接 / 🟡连接中 / 🔴已断开
3. 连接断开时自动重连（指数退避：1s → 2s → 4s → 8s，最多 5 次）
4. 重连失败后显示手动"重新连接"按钮
5. 通过 WebSocket 接收：
   - 试验状态变更推送 → 更新控制面板状态
   - 日志消息推送 → 追加到日志区
6. 离开控制台页面 → 断开 WebSocket 连接

**状态流转规则：**
```
IDLE → (载入方法) → LOADED → (开始执行) → RUNNING
RUNNING → (暂停) → PAUSED → (继续) → RUNNING
RUNNING/PAUSED → (停止) → COMPLETED
任何状态 → (异常) → ERROR
```

**试验详情/历史数据：**
1. 试验完成后可在控制台查看：
   - 试验基本信息
   - 状态变更历史时间线（载入 → 开始 → 暂停 → 继续 → 停止）
   - 测点历史数据简要概览（后续可跳转 M9 分析页面）

## 8. 数据驱动架构要求

### 8.1 核心理念

> **界面是数据的投影，操作是向数据发送指令。**

前端不拥有业务数据，只投射和呈现后端的状态。

### 8.2 具体要求

| 要求 | 说明 |
|------|------|
| **单一数据源** | 前端所有业务状态来自后端 API，不做本地业务数据缓存。仅认证 Token 和用户偏好可本地存储 |
| **操作即指令** | 用户在界面的所有操作（CRUD、执行控制）都转化为后端 API 调用，前端不自行计算业务结果 |
| **状态驱动 UI** | 每个数据组件都有三态（Loading / Data / Error+Empty），状态自动驱动 UI 切换 |
| **无假数据** | 所有数字、文本、状态值必须来自后端真实数据。无数据时显示适当空状态，禁止占位符 "-" |
| **统一数据获取** | 同一数据不在多个组件中重复请求。数据获取集中管理，多组件消费同一数据源 |

### 8.3 状态管理规范

每个需要后端数据的页面/区域应遵循以下状态模型：

```
状态：IDLE → LOADING → LOADED (有数据) / EMPTY (数据为空) / ERROR (请求失败)
```

| 状态 | UI 表现 |
|------|---------|
| IDLE | 初始状态，尚未触发数据加载 |
| LOADING | 骨架屏或加载动画，不可交互 |
| LOADED | 正常展示数据，可用交互 |
| EMPTY | 无数据时的引导提示 + 操作入口 |
| ERROR | 错误信息（用户语言）+ 重试按钮 |

## 9. 国际化要求

### 9.1 框架要求

- 建立多语言支持框架，架构上可扩展至任意语言
- 所有面向用户的文本（按钮、标签、提示、错误消息）必须通过国际化机制获取，**禁止硬编码任何语种的文本字符串**
- 使用标准 `.arb` 文件（Application Resource Bundle）管理翻译

### 9.2 支持语言

| 语言 | 代码 | 优先级 | 说明 |
|------|------|:------:|------|
| English | `en` | **默认** | 回退语言，所有文本必须有英文翻译 |
| 中文（简体） | `zh` | 必须 | 与英文并列完成 |

### 9.3 具体要求

1. 所有面向用户的文本必须同时提供英文和中文版本
2. 语言切换立即生效，无需重启应用
3. 语言偏好持久化到本地存储
4. 数字、日期、时间格式跟随当前语言（英文：`MM/DD/YYYY`，中文：`YYYY-MM-DD`）
5. 后端返回的错误消息如果是英文，前端不翻译（保持后端原样），但前端自己产生的错误提示必须双语

## 10. 移动端适配要求

### 10.1 响应式断点

| 断点 | 宽度范围 | 设备类型 | 布局策略 |
|------|----------|----------|----------|
| 小屏 | < 600px | 手机竖屏 | 单列布局，导航转为底部 Tab Bar 或汉堡菜单 |
| 中屏 | 600px - 1200px | 平板/手机横屏 | 双列布局，侧边栏可折叠 |
| 大屏 | > 1200px | 桌面 | 完整布局，侧边栏常驻，多列展示 |

### 10.2 适应性要求

1. **导航适配**：
   - 大屏（>1200px）：左侧 NavigationRail 或侧边栏常驻
   - 中屏（600-1200px）：侧边栏可折叠（NavigationRail 窄模式）
   - 小屏（<600px）：底部 BottomNavigationBar + 顶部 AppBar 汉堡菜单
2. **表格/列表适配**：
   - 小屏：表格转为卡片列表，列数减少，隐藏次要列
   - 数据显示优先级：名称 > 状态 > 时间 > 其他
3. **图表适配**：
   - 图表应随容器宽度自适应
   - 小屏上，控制面板和图表区上下排列（而非左右）
   - 触摸交互：支持单指平移、双指缩放
4. **对话框/表单适配**：
   - 小屏上全屏对话框代替弹出式对话框
   - 表单字段宽度自适应
5. **试验控制台特殊适配**：
   - 小屏：控制面板和日志区上下堆叠（而非左右）
   - 控制按钮保持可用大小（最小 48x48dp 触摸目标）
6. **最小支持宽度**：360dp（小屏手机标准宽度）
